# 面向 AI 的内容写作

编写让 AI 能够准确理解和使用的内容。指令提供判断与行动的方法，知识提供事实、概念和依据；根据读者的任务，决定写什么、怎样组织，以及怎样让需要的内容被及时找到。

以正确理解和实际使用为目标：让合适的知识在合适的时机出现，保留重要约束，使 AI 能完成任务并判断何时已经充分。内容长度、文件结构和封装形式服务于这个目标。

业务研究与事实核实、Wiki 的持续维护、源码研究和实施规格沿各自的领域工作流推进。本 Skill 提供面向 AI 的写作与组织方法，结合这些工作已有的内容、所有权和验收要求使用。

## 1. 明确读者与写作目的

阅读当前请求、已有决定、目标原文及相关引用，结合真实场景确认：

- AI 在什么任务下使用这份材料，要理解、判断或完成什么。
- 需要提供哪些事实、知识或操作能力，哪些有效行为和约束需要保留。
- 修改已有材料时，当前具体问题是什么；怎样的结果表示目标已满足。

已有明确需求或局部改动时，直接利用这些输入。新建或重整复杂能力时，用少量真实问题明确职责、关键取舍、输入输出和验收场景；记录到已有讨论或任务材料，形式和数量服从问题。

需要判断的任务，说明选择依据和正确停止方式；确定性操作，明确权限、输入输出、副作用与失败处理；知识资料，说明概念关系、事实依据和适用条件。让设计意图落实到内容和使用方式中。

## 2. 理解现有内容与使用路径

通读目标内容及任务相关的引用资源，核对来源、调用方式和使用场景。修改涉及职责、行为或结构时，沿实际入口追踪正文、详细资料、工具与使用方，确认当前权威版本。

分清已确认规则、可核实事实、工作假设和候选方案。知识需要补充时，从所属领域的真实来源取得依据；尚无证据的内容保留明确状态。

修改已有材料时，判断问题来自知识缺失、表达含糊、入口不清、来源重复或冲突、组织失序，还是原有规则本身不成立。针对原因确定修改范围。

授权、数据、安全、兼容和停止边界按当前有效语义保留；需要改变的行为以用户已确认范围为依据。原有内容已满足目标时，认可并结束；只缺入口或局部修正时，在对应位置完成。

## 3. 安排知识归属与信息层级

每项内容确定一个权威来源，并安排需要它的任务如何找到它：

| 内容的作用 | 适合的位置 |
| --- | --- |
| 跨任务个人偏好、决策权与执行边界 | 个人 `AGENTS.md` 的简短常驻规则 |
| 特定项目或目录内持续生效的约束 | 对应范围的项目规则 |
| 判断何时选用一项能力 | Skill 的 `description` |
| 选用后各分支共同需要的判断与主流程 | `SKILL.md` 正文 |
| 只在部分任务需要的概念、事实和详细方法 | 有明确读取条件的参考资料或领域文档 |
| 重复、确定且容易出错的操作 | 随能力维护的脚本与必要依赖 |
| 可直接核实的配置和运行事实 | 原有代码、配置、命令或外部权威来源 |

按适用范围、错误后果和发现可靠性决定哪些规则常驻。迁出重要约束前，明确接收位置与读取条件，并保留其效力；只有路径的链接需要补足任务条件。

同一概念的定义、规则和例外放在一起；不同分支的详细知识按需展开。文件拆分的收益来自实际读取路径，每条任务路径只加载需要的内容。

重整常驻规则时读取 [规则文档](references/rule-documents.md)；需要设计知识入口或调整层级时读取 [组织与入口示例](references/content-patterns.md)。

## 4. 编写内容与入口

- **围绕内容的用途组织。** 有顺序要求时呈现主流程；参考资料按概念、关系与适用条件组织。必要的背景、依据和例外与对应内容就近放置。
- **用自然、准确的词表达。** 采用使用者和领域已有的语言，正向描述目标行为；需要硬性限制时写明边界与允许的行动。
- **写出关键判断。** 保留会改变选择的取舍、生命周期和失败语义，使 AI 能处理未见过的变体，并知道当前任务何时已经充分。
- **让入口表达选择。** 写清任务条件、目标材料及其作用。Skill 描述表达能力与触发边界；执行步骤和工具用法放在选用后读取的内容中。
- **按整体意图修改。** 保留有效表达，把变化融入已有职责与结构，统一重复或冲突的语义，更新受影响引用。
- **逐项判断内容价值。** 保留有实际作用的知识、约束和示例；已有权威来源直接提供的事实留在原处。以真实使用和证据判断哪些提醒仍有用。

模板用于稳定输出契约，示例用于说明难以从规则看出的差异。内容长度与结构服从任务；把只在部分场景需要的长篇细节放到对应参考资料。

目标是 Skill 时，读取 [Skill 封装与工具](references/skill-engineering.md)，完成名称、描述、资源归属和必要的工程步骤。

## 5. 核对质量与实际使用

先核对内容是否准确、忠实满足用户目标、保留原有约束，再选择足够证明本次变化的检查：

| 变化 | 直接检查 |
| --- | --- |
| 含义保持不变的校对 | 完整差异；涉及结构或路径时加解析和引用检查 |
| 知识和表达的调整 | 核对来源、适用条件、概念关系和引用，检查读者需要的依据是否完整 |
| 脚本、资源或路径变化 | 相关现有测试、代表性调用与脱离原工作目录的资源解析 |
| 新增能力，或改变触发、判断、授权、执行与停止方式 | 在新上下文中检查对应自然请求的实际选择、动作与产物 |
| 需要判断候选是否优于原版 | 同一环境与初态下比较原版和候选；关键结果有波动时补充试验 |

涉及行为检查时读取 [评估设计](references/evaluation-design.md)；需要用本地 Codex 执行时再读取 [运行工具](references/codex-evaluation.md)。案例来自真实任务与已确认契约；正确认可、适时结束和相邻任务的选用边界也是有效结果。

检查入口是否能够触达材料、材料是否支持正确理解与决策、重复来源和冲突是否消除。必要证据已经充分时结束验证；新的差异、实际失败或会改变结论的疑点再触发后续检查。

交付时说明改了什么、保留了什么、哪些验证已运行，以及证据的覆盖范围。用户要求先审阅候选时，交付独立文件与清楚的状态，采用与替换按后续确认推进。
