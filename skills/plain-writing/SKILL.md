# 把话说清楚

让读者读完就知道发生了什么、为什么、接下来怎样处理。每句话都服务于理解或决定。

## 先核实前提，再形成判断

写作前先想清楚读者要判断什么，从已有证据中选出能够回答它的事实。

把提问拆成实际观察、隐含前提和待解释原因。处理测试报告、Issue 或他人建议时，先核对实际请求、现有业务规则和实际结果，再形成判断。用户描述、第三方报告和 AI 结论都提供线索，判断由事实支持。前提与事实有出入时，先讲准确事实，再解释实际发生的事情。

例如，问“为什么天空是绿色的”时，先核实实际场景与天空颜色，再解释眼前景象。业务反馈同样先判断实际结果与业务预期的关系，再讨论原因和处理方式。

例如，话题搜索中的粉丝数条件留空，会允许粉丝数为零或空的作者进入结果；这些数值的来源再沿采集和保存过程解释。筛选条件解释“为什么选中了这个作者”，采集过程解释“为什么这个字段是空值”。

沿用已有调查和用户确认的结论。尚待核实的内容用一句具体的话说明证据缺口。

## 直接讲因果

先写读者关心的判断或结果，再写决定这个结论的原因。用具体的主体和动作连接前后过程，让读者看见事情怎样发生。

解释字段缺失时，说清接口返回了什么、代码读取了什么、最终保存了什么。每一步的说法由相应证据支持；代码中的字段定义只代表代码的约定，供应商的真实响应另需实际样本核实。

信息量随问题调整。短评论通常一两段；多个需要分别判断的结论可以分点。读者已经给出的背景直接承接。

## 使用正向表达

遵循个人 `AGENTS.md` 中的规则：严禁使用任何否定词。

直接陈述原因、结果、适用条件和做法。把防御、反驳和自我辩护改写成读者需要的事实。明确表达自己的判断与对方建议各自的依据。

在准确表达事实的基础上，用正向句式说明具体状态和处理办法；证据缺口可写成“原始响应待核实”。

## 使用日常词和具体动作

按读者理解事情的方式表达。必要的 API 名、代码标识符和专业术语保持准确，并解释它们在这里做什么。

- 写“把帖子里的作者信息保存下来”，让读者理解原先所谓“作者归一化”具体做了什么。
- 写“返回前查一次账号详情，补齐粉丝数”，说清所谓“完善数据交付”的动作。
- 写“请求超时后再次提交，产生了两笔收费”，直接说明所谓“幂等性问题”的触发与影响。

证据链接放在对应结论旁边，详细日志和实现说明留在读者需要继续核实时的位置。

## 按文字的用途选择重点

| 场景 | 读者需要的内容 |
| --- | --- |
| Issue、测试反馈 | 这次请求为什么得到这个结果，按业务规则应怎样判断，必要的后续动作 |
| PR 说明 | 什么场景受到影响，修改后怎样工作，验证结果 |
| Changelog | 用户做什么时会遇到什么变化；修复项写具体触发和现在的行为 |
| 进展 | 新发现及其影响，下一项能解决疑点的动作 |
| 调查结论 | 有证据支持的原因，仍待核实的关键事实，当前能够确定的处理方向 |
| 简单问答 | 直接回答当前问题，补充理解答案所需的信息 |

具体动作胜过“优化体验”“提升稳定性”之类概括。例如 Changelog 写“修复付款超时后重试产生重复扣费的问题：同一笔付款的重试现在会继续原交易”。

## 发出前精简

默读一遍，只保留有作用的句子：

1. 开头直接回答读者当前关心的问题。
2. 原因与结果连贯，重要结论都有事实支持。
3. 每句话提供新的信息，或帮助读者作决定。
4. 用具体主体和动作说明事情，详细证据放入链接。

删去重复背景、自我评价、形式化的调查流程介绍和空泛收尾。篇幅服从理解需要，结论、必要原因和关键证据已经清楚时结束。
