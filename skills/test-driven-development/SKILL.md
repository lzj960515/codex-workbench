# Test-Driven Development

## 目标

用可观察的业务行为约束实现，让测试证明需求和根因，而不是复刻内部代码结构。

## 执行流程

1. 把需求转成行为契约：输入、可观察输出、副作用、错误语义和不变量。先确认现有测试、调用方和兼容约束。
2. 按风险选择最小有效边界：纯逻辑用单元测试，模块协作用集成测试，真实存储或队列语义用受控本地依赖。遗留重构先用 characterization test 锁定需要保留的行为。
3. 写一个能够因为缺少目标行为而失败的测试。运行它，确认失败原因与需求一致，而不是配置、fixture 或无关错误。
4. 写使该测试通过的最小生产代码。避免同时引入未经需求证明的抽象或顺手重构。
5. 在测试保护下整理职责、命名和重复代码。每次结构调整后保持相关测试通过。
6. 增加关键边界和失败路径，再运行受影响模块的回归测试。共享契约或跨模块改动扩大验证范围。

## 测试设计

- 测试公开行为和稳定契约，不依赖私有方法或偶然实现顺序。
- Mock 外部边界和昂贵依赖，不 Mock 被验证的核心职责。优先使用项目现有 fixture、Provider mock 和可重复的本地数据。
- Bug 测试应在旧实现上稳定失败，并覆盖真正的触发条件。
- 纯文档、生成产物和无行为变化的机械修改使用更合适的静态检查，无需制造没有证明力的测试。

## 完成标准

报告 RED 阶段的失败原因、GREEN 阶段的定向结果和最终回归范围。无法运行某层测试时，明确说明替代证据与剩余风险。
