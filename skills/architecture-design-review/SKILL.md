# Architecture Design Review

## 目标

为已经确认的能力建立完整且一致的系统模型，让它自然落入稳定抽象，同时保持产品责任和实现范围与当前目标一致。讨论尚未确认的方向时，先比较目标与取舍；目标确认后，架构设计负责实现它所需的完整职责边界。

完整模型用于看清当前能力在系统中的所有影响，不代表把每一种可能的扩展都建设出来。每个新增公共接口、状态、持久化、调度、恢复、兼容机制和抽象都应由当前目标、既有契约、已证实风险或已知 Roadmap 中当前阶段需要的职责接缝支撑。缺少某项能力会使当前验收失败时，它属于完整模型；只会改善体验、增加通用性或服务未来复用时，它仍是候选方向。完整生命周期检查负责发现需要核实的问题，当前系统证据负责决定哪些机制进入实现。

架构设计负责调查并推荐职责与模型，按适用的 `AGENTS.md` 区分方案判断和数据变更授权。用户确认功能目标后，仍按具体批准范围实施模型变更；新的用户交互、支持平台和运行承诺也以已确认范围为准。现有系统的关键代码、契约或环境事实不可用时，把组件形态和技术选择保留为待证实方案；用户明确要求从零设计时，才基于标明的假设形成绿色项目模型。

## 工作方式

1. 明确当前是在比较候选方向还是设计已确认目标；分开写出已经确认的用户可见结果、由当前证据证明的必要系统行为、现有契约、证据尚未决定的事项和不属于当前阶段的候选能力。
2. 阅读与问题相关的完整路径和同类历史做法：入口、写入、处理和使用方，按影响追踪展示、恢复、公共类型、模块装配、测试和运行时边界。已有成熟框架时，同时核对其原生术语与生命周期。
3. 从已确认业务动作和真实约束出发，先检验沿用现有模型的完整方案，再比较必要的新模型。明确概念、所有权、生命周期和不变量，按新增事实来源、持久状态、平行分支、迁移及维护的总体成本推荐；现有名称或候选测试不能代替业务依据。涉及待确认的数据变更时，交付具体清单、复用方案的不足及使用方影响，确认后再进入依赖该模型的实现。
4. 按生命周期归类当前需要的数据：定义期固定规则用 `Config`，实例创建参数沿用宿主框架命名，调用期可变参数用 `Options`，运行中数据使用明确的 State 或 Context。
5. 同时检查缺失与多余的职责。每个类承担一个稳定且可命名的职责；先判断代码应归入现有所有者、合并或删除，再判断是否确实缺少抽象。重复状态机按相同业务语义与生命周期收敛；简单字段转换和顺序调用按实际需要使用函数或具名方法。
6. 从使用者视角审查公共 API。设计或重划模块接口、依赖位置与测试边界时，读取 [Codebase Design](references/codebase-design.md)，判断封装隐藏了哪些复杂性、调用者需要掌握哪些契约，以及变化是否集中在真实职责所有者。保持类型推断和领域意图；本 Skill 的生命周期与范围约束共同决定设计。
7. 检查当前能力的完整运行模型：成功、失败、重试、幂等、多实例、恢复、持久化、可观测性和兼容性。持续支持的协议或公共契约属于最终模型；为本次切换临时保留的路径明确保护哪个真实消费者或版本组合、由谁持有，以及何时退出；执行替换沿用 `maintainable-implementation` 的消费者核实与退出流程。根据风险的发生概率、损失和恢复成本选择机制强度，把未来能力本身留作候选。
8. 将发现分类为确定 Bug、一致性问题、功能缺口、业务模型问题或架构债务。一起处理当前目标需要、同根因且风险可控的问题，其余形成明确的后续边界。

## 输出与实施

- 设计讨论先给推荐模型、关键取舍和被否决方案的实质原因。
- 已确认目标的实施方案说明职责如何保留、原地修改、替换退出或临时共存，给出仍需证据决定的事项与未纳入实现的候选能力。重新推导是校正设计的方法；已有结构符合目标时保持它，代码行数和重写次数不作为质量标准。
- 审查先核对模型选择的必要性与授权，再判断实现是否成立；从原始用户目标验证复用现有模型能否得到同一结果。存在问题时给出职责或数据流证据，必要性、授权与实现均成立时认可当前设计。
- 实施时让改动融入现有结构，并补齐与风险相称的测试和文档。
- 小型且模式明确的改动保持轻量；沿用适用的授权边界，调查与交付材料按实际风险安排，已有充分依据可直接复用。
