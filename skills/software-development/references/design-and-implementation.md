# 设计与实现判断

在模型复用、职责归属、接口、生命周期、替换或失败处理存在实质选择时，读取本页对应部分。依据真实业务动作与调用方契约选择实现规模；已有职责清楚的局部修改，沿原位置完成即可。

## 业务动作与调用方契约

用真实场景解释代码：谁通过哪个入口完成什么动作，哪些数据进入处理，谁使用结果，失败后留下什么状态。沿当前影响核实写入、处理、读取、展示与恢复，结合类型、项目规则、同类做法和已有运行事实判断。

框架与基础设施也有具体使用者。例如“取消一次任务后释放它持有的资源”就是调用方契约；其资源所有权、取消时机和错误传播决定实现。编译约束、安全隔离、持久化一致性与失败语义同样属于必须保持的结果。

设计依赖实际用量、成本、时效或性能时，取得范围相称的直接证据，区分配置上限、实际请求、返回结果和有效产出。关键代码或契约不可用时，明确尚待证实的选择；从零设计按用户允许的范围标明假设。

## 模型简单的含义

先检验沿用现有模型与处理链路能否完整满足目标，再比较确有必要的新方案。名称、分类或外观不同只是调查线索；新增独立事实来源与平行流程的依据，是现有契约无法表达的真实行为差异。

围绕每个模型判断：

- 它表达哪个业务事实或稳定规则，谁写入、谁读取，何时创建、改变和失效？
- 现有模型在哪个具体场景下无法保证约定结果？原地修改会破坏什么语义或约束？
- 新方案增加多少概念、持久状态、分支、迁移、使用方改动、兼容与恢复责任？这些总成本换来了什么当前收益？
- 当前目标去掉这个模型后，哪项结果会缺失？模型成立的依据来自业务、调用方与运行契约，而非候选测试或实现投入。

简单是完整承担当前必要责任，同时减少重复事实来源和长期维护负担。较少的表、类、方法或代码行数只描述形式；把复杂性推给调用方、兼容分支或人工恢复同样计入成本。已知后续需求用于检验职责能否自然扩展，未来行为与运行机制留待对应需求。

数据模型变更的确认条件以适用的 `AGENTS.md` 为准。必要性分析形成提案，功能目标确认与具体数据变更授权分别判断；待确认的模型及其依赖实现按该边界推进。

## 职责、代码位置与生命周期

代码归入拥有业务规则、相关数据变化与失败结果的职责。判断一个位置是否合适，看同一种业务变化是否集中在这里、调用方是否仍需重复协调细节，以及同名代码是否真的承担相同语义。

- 现有所有者稳定，新行为自然落在其词汇和生命周期内时，原地扩展。
- 多种生命周期、变化原因或无关职责挤在一起，调用方反复安排同一组底层动作，或新增能力没有自然所有者时，调整承担完整责任所需的边界。
- 同一种状态管理、调度或持久化机制第三次出现时，重新核对共同语义、状态所有权与生命周期；表面相似而业务含义不同的流程分别处理。
- 每个类、函数和模块能说明为何存在。提取方法用于表达业务动作；引入策略、工厂、仓储或协调对象，要能指出真实协作关系与被隔离的变化。

框架已有术语、参数结构和生命周期时优先沿用，自定义抽象只承载框架尚未表达的领域含义。自定义 API 的定义期固定规则可用 `Config`，调用参数可用 `Options`，运行中数据采用准确的状态或上下文名称；实例创建参数遵循宿主框架命名。扩展框架能力时，先补齐当前缺失的概念，使能力自然落入一致模型。

| 实现位置 | 成立依据 |
| --- | --- |
| 局部表达式或具名方法 | 规则或转换属于调用方同一次执行，共享其状态、失败与重试边界。 |
| 类或领域服务 | 稳定职责拥有规则、依赖或确有意义的变化，需要集中管理。 |
| 独立任务或工作流环节 | 当前契约需要独立调度、重试、并发、限流或恢复，输入与完成结果能被清楚表达。 |

多个步骤能被命名，并不自动需要多个执行阶段。大量检查点可能意味着混合了不同业务动作；大量只传递中间结果的小任务，也可能原本属于一次业务尝试。按真实失败与运行生命周期选择边界。

## 公共接口与核心基础设施

修改公共 API、共享状态、跨模块职责或引入新生命周期时，按实际影响加深检查：调用者、输入输出、调用顺序、不变量、可变性、状态持有者、失败和取消、资源释放，以及受支持的部署与兼容组合。

接口包括调用方必须知道的所有条件，既有类型和方法，也有顺序、配置、错误与必要的性能约束。好的封装让调用者掌握更少细节，并把同一变化集中到真实所有者：

- 调用者可以直接表达业务动作，还是必须了解内部组件和安排重复步骤？
- 去掉封装后，复杂性会消失，还是重新分散到多个调用者？有用的封装承担了真实规则与协调责任。
- 内部细节是否通过参数、标志和中间对象泄漏？必要约束是否依然清楚可见？
- 合并职责后是否仍有一致的生命周期与变化原因？参数或方法减少本身不证明接口更好。

存在会改变采用决定的实质方案时，在相同事实与已确认用例下比较接口、调用例、隐藏的复杂性、依赖和总维护成本，再给出推荐与原因。已有方案成立时直接采用；单独设计任务可以交付模型、契约、取舍与未决事项，代码实现服从当前授权。

生产职责与既有框架决定依赖边界，测试利用这些边界。远程调用或第三方服务本身不要求再建一层接口；依赖注入、适配器和内部可替换位置须有真实所有权、生命周期、隔离或变化依据。

## 复用现有能力与选择实现

优先寻找所属模块的领域动作、内部共享能力和已经使用的成熟库，再考虑项目内的小实现。比较语义、错误与取消模型、依赖生命周期、适配成本和维护责任，选择能完整表达当前契约的方式。

解析、协议、安全、缓存、并发等复杂能力与现有库的契约匹配时，在它支持的边界使用；简短领域规则、局部转换，或使用库反而增加大量适配与运行责任时，留在所属业务位置实现。通过原生 API 复用成熟能力，避免抄写其内部算法后自行承担维护。

包装层用于表达缺少的领域含义或隔离当前存在的提供方差异。只有转发、重命名或为假想替换保留入口的层，重新检查是否仍有必要。

## 可读的业务顺序

高层方法保持一个抽象层级，按业务动作排列，使阅读入口就能看清输入、决定、外部动作和结果。底层方法承担实际规则与技术细节，方法名从调用者和领域阅读者视角表达意图。

多步骤表达式、转换和异步链使用中间变量与具名操作；一眼可懂的局部转换保留内联回调，业务规则、副作用与多阶段异步流程使用明确动作。复用类型与输入输出契约集中到所属类型边界，实现文件聚焦行为。

保存、付款与发布事件等副作用由真实职责拥有，并让顺序和失败点可见；采用返回值还是状态变化，由业务与宿主框架决定。测试适应生产行为，不能以可测试性为由强制纯函数化或增加额外接口。

注释说明命名无法表达的业务原因、生命周期约束、失败语义与关键不变量。从入口复读结果，确认每个类和方法的存在理由、代码归属，以及相关变化能否沿现有职责自然扩展。

## 完整替换与兼容

替换职责时明确原地保留、修改、移除和临时共存的内容，在真正所有者中实现目标行为并切换实际调用方。按同一责任检查入口注册、分支、转发层、配置、类型及相关文档，退出被取代的旧路径。

持续支持的协议和公共契约属于最终模型。临时保留的路径则明确真实消费者、部署版本组合、可重放数据或回滚需求，并在现有任务或发布材料记录所有者与退出条件。代码搜索无引用、队列为空或短期没有访问各自只提供部分证据；涉及在途工作时核实其实际处理与恢复方式。

内部名称随职责更新，外部协议名称按消费者契约处理。被移除实现对应的测试与说明按其行为是否仍需保护决定保留或退出；相邻债务留在独立后续范围。调查不会自动授予生产修改或删除数据的权限。

## 异常、防御与损失容忍度

默认由既有应用、队列、任务或传输边界记录失败并承担重试。`try/catch` 放在能够明确恢复、转换稳定领域错误、释放资源、补充外层无法获得的必要上下文，或执行已确认部分成功语义的位置；操作仍然失败时让失败继续传播。

新增重试、兜底、锁、默认值或忽略异常前，判断：

- 哪个受支持的输入、生产者或真实信任边界会触发？对应哪个明确契约或可信风险？
- 会失去什么业务结果，损失概率、后果与恢复成本如何？既有失败处理或人工恢复是否足够？
- 新机制放在哪个所有者中，调用者看到什么结果？它是否掩盖失败、重复外层重试或占用原有预算？
- 相比正常主流程，它增加的状态、分支和维护责任是否值得？

按已确认损失容忍度取舍，接受的重启漏跑、偶发重复继续作为验收边界；重大资金损失、越权、租户隔离和不可恢复数据损坏保留必要保护，明确安全不变量可直接证明保护的必要性。对低概率且影响有限、缺少实际契约依据的问题，保持既有失败处理与清楚的超时、重试预算。

部分成功要能说明哪些数据可跳过、哪些失败必须上抛，以及最终结果如何被用户或下游理解。统计、日志和成本计量等辅助写入独立于业务成功，失败不阻断采集、付款或内容入库，也不侵占原业务的超时与重试预算；已接受的重复或计量缺口保留可说明的统计边界。
