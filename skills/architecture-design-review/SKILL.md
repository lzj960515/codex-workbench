# Architecture Design Review

## 目标

先建立完整且一致的系统模型，再判断局部代码。让新能力自然落入稳定抽象，而不是围绕当前需求堆叠参数、分支和协调器。

## 工作方式

1. 阅读与问题相关的完整路径：公共类型、调用链、模块装配、持久化、测试、文档和运行时边界。已有成熟框架时，同时核对其原生术语与生命周期。
2. 用简短模型明确稳定概念、所有权、生命周期、状态边界和不变量。区分什么长期稳定、什么会随业务变化。
3. 按生命周期归类数据：定义期固定规则用 `Config`，实例创建参数沿用宿主框架命名，调用期可变参数用 `Options`，运行中数据使用明确的 State 或 Context。
4. 检查职责归属。每个类承担一个稳定且可命名的职责；无处自然安放的代码通常意味着职责边界或抽象仍不完整。重复出现的状态机、协调协议或收尾逻辑优先收敛为共同机制。
5. 从使用者视角审查公共 API：直接表达领域意图，保持类型推断，减少嵌套、中间 Builder、隐式状态和实现细节泄漏。
6. 检查完整运行模型：成功、失败、重试、幂等、多实例、恢复、持久化、可观测性、兼容性和未来扩展。只针对真实风险增加复杂度。
7. 将发现分类为确定 Bug、一致性问题、功能缺口、业务模型问题或架构债务。一起处理同根因且风险可控的问题，其余形成明确的后续边界。

## 输出与实施

- 设计讨论先给推荐模型、关键取舍和被否决方案的实质原因。
- 代码审查先列具体问题和位置，再说明整体职责或数据流问题。
- 实施时让改动融入现有结构，并补齐与风险相称的测试和文档。
- 小型且模式明确的改动保持轻量；无需为了使用本 Skill 强制创建设计文档、worktree、子代理或额外审批阶段。
