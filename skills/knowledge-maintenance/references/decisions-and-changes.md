# 决定与变更记录

本页用于写独立变更记录，以及维护方案、决定、实施状态与历史关系。

## 各类内容保存什么

| 位置 | 保存的知识 |
| --- | --- |
| 当前主题页 | 现在怎样工作、适用条件与核验入口 |
| 已有方案或 `plans/` | 要解决的问题、候选或已确认方案、未决事项和实施进度 |
| 决定记录或 `decisions/` | 需要独立长期引用的选择、真实理由、前提与取舍 |
| `changes/` | 本次为何改变知识或行为、作了什么决定、解决什么问题，以及实际结果 |

简短理由就近留在主题或方案；确有长期引用需要时再建立独立决定。沿用已有权威计划、规格、决定和进度入口，知识维护负责依据证据修订说明及关联关系。

## 围绕决定写变更记录

后来者需要理解当时遇到什么问题、为何采用这个处理方式、结果改变了什么。记录从这些信息组织，文件清单与验证细节只作为必要证据。

一份记录通常只需几段，可以使用以下结构，简单变化合并表达：

```markdown
# 解决了什么问题或作出了什么决定

## 背景与问题

谁在什么场景遇到什么问题，造成什么影响；为什么现在需要改变。

## 决定与理由

本次确定采用什么做法，为什么适合当前目标；有真实取舍时说明关键理由。

## 结果与边界

已经改变或证实什么，解决到哪一步，什么尚未完成或验证。
链接当前说明、相关决定及支撑结果的证据。
```

没有新增决定的事实修正，说明新证据如何改变旧理解即可。尚在讨论的内容写成提议与理由；只核实了配置就写配置结果。预期收益与实际效果分开，缺少度量时不编造成效。

例如，费用工具从个人目录移入项目：背景是它依赖团队账号与工作空间任务，个人入口会让其他项目也看到这项专用能力；决定是由该项目维护 Skill，并更新原定时任务的读取路径，复用现有调度以保持费用口径和投递规则；结果说明路径已切换、下一次实际采集尚未验证。具体文件和命令只需链接到当前说明。

## 记录何时创建、怎样维护

默认使用 `changes/YYYY-MM-DD-<主题>-<任务标识>.md`，具体根目录与命名沿项目规则。日期取首次记录日期，主题用英文 kebab-case，任务标识沿项目约定；没有现成标识时可生成短随机标识。

同一任务、同一主题在交付或合入前续写同一记录，独立任务分别成文。已合入记录需要更正时，新记录链接原记录及修订后的主题，保留当时的事实与理由。

记录通过目录、日期和搜索发现。`changes/README.md` 只说明用途、命名和写法，日常维护不逐项登记新记录，也不新建或追加集中日志。已有旧集中日志作为历史证据查阅；当前任务不因此承担全量历史迁移。

业务行为、知识结论、设计依据或阅读路径发生实质变化时记录。只读答疑、没有修复的检查、错字和格式调整直接在对应结果结束，不为凑记录虚构背景或决定。

## 用证据维护状态与演进

方案的提议、确认、实施、完成、放弃或被取代，与决定的有效性分别表达。状态依据已有讨论和实际结果，必要时注明日期与适用范围。

确认选择不代表已经实现；实现、合入、发布、数据迁移和运行验证分别说明证据。部分能力已上线、部分只完成本地实现时，在当前说明和方案中准确区分，缺少证据的环节保持未知。

方案落地后，将已证实行为融入当前主题，原方案保留实际完成范围、剩余事项和实现依据。决定被取代时保留当时的约束与真实理由，链接后继选择；仍然有效的决定不因已经实施而归档。

归档表示材料退出日常指引。当前入口优先指向现行说明，历史材料保留状态、原因及后继链接；没有真实需要就保持原路径。原始材料保留原貌，对适用时期的说明放在知识页面或导航中。
