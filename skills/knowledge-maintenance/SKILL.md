# 知识研究与维护

让读者能找到可信的当前知识，理解它的依据，并在事实变化后知道该修订哪里。资料摄取、源码研究和后续答疑共用这一维护方法；研究深度和交付形式由当前问题决定。

## 1. 确认问题与交付范围

结合用户请求和已有决定，确认要回答什么、服务谁，以及本次交付是对话解释、知识页面修订、新建知识库，还是检查现有知识。

先读目标项目的规则、文档入口和相关页面，找到知识归属、已有来源及维护约定。沿用现有权威页面和阅读路径；局部问题只补足理解它所需的背景。需要持久化的研究，把结果融入现有知识库；只要求解释或检查时，在对应结果充分后结束。

源码、原始笔记、运行记录和外部文献是核验依据，知识页面承载经过组织的当前理解。先分清本次要维护的页面与作为证据的原始材料；知识整理本身不授权修改来源代码、原始记录或运行系统。

## 2. 取得足以支持结论的依据

从已有知识定位证据，围绕会影响答案的缺口查阅原文、代码、配置或可用运行记录。记录有意义的来源日期、版本、环境与适用范围，使关键结论能回到具体证据核实。

- 已确认事实说明证据；综合判断说明推导依据。
- 来源不一致时比较适用范围、时间与权威性，保留尚不能消除的分歧。
- 未知和候选方案保持明确状态；缺少历史理由时，区分对现有设计的解释与实际发生过的决定。

研究源码仓库、机制或演进时，读取[源码研究与讲解](references/source-research.md)，选择当前问题需要的概览、机制或演进方法。普通资料整理无需加载源码研究细节。

## 3. 形成答案或更新当前知识

| 当前任务 | 应完成的结果 |
| --- | --- |
| 依据知识答疑、解释机制 | 引用相关页面与必要来源，解释结论及适用边界；只读请求在回答后结束 |
| 摄取资料、沉淀研究 | 找到新事实与既有知识的关系，融入最接近的权威页面；独立主题才新建页面 |
| 修订结论 | 让正文表达有证据的当前理解，同步受影响的摘要、状态和交叉引用 |
| 检查知识库 | 核对冲突、过期内容、重复解释、孤立页面、失效链接与关键证据缺口；有修复授权时落实到文件 |

页面围绕读者的问题组织，开头交代用途、适用范围和必要状态。完整解释在所属页面维护，其他阅读路径通过链接进入。名称相似但语义不同的概念，先说明边界再决定是否合并。

需要创建知识库、调整分类与导航、处理知识冲突或合并页面时，读取[知识组织与修订](references/knowledge-organization.md)。只做局部修订时，保持仍然准确的导航和目录。

## 4. 保留决定与变化的理由

先更新当前知识，再同步必要的入口、关联方案与决定。采用逐层 `README.md` 导航和 `changes/` 独立变更记录；新内容直接进入所属目录，日常维护不追加集中日志或另设平行索引。

变更记录围绕背景、决定及其理由、解决的问题与实际结果展开。记录让后来者理解变化的原因；完整机制留在主题页，执行进度留在已有计划或任务系统。仅查阅、无修复的检查和机械校对无需另写记录。

写变更记录，或涉及提案、决定、实施状态和历史取代时，读取[决定与变更记录](references/decisions-and-changes.md)。确认选择、完成实现、合入、发布和运行成功分别依据证据表达。

## 5. 核对并结束

先核对结果是否回答原始问题，范围是否符合请求，再检查：

- 关键结论有来源，事实、解释、候选与未知保持准确；没有把设计推导写成真实历史。
- 知识变化已经进入正确页面，受影响的链接、摘要与状态一致；新增或移动的页面可以找到。
- 变更记录说明真实背景与选择理由，实际效果和未验证范围清楚；没有把操作步骤堆成记录。
- 本次不再需要的临时快照、草稿和运行输出已清理；待继续的交接材料与必要证据有明确用途，需长期保存的内容进入所属文档。

现有知识已经足够或检查未发现问题时，直接给出依据与检查范围。交付时说明答案或修订结果、关键依据以及尚未确认的事项。
