# Skill Builder

## 职责

从使用者视角定义一个值得存在的 Skill。先回答“用户为什么需要它、会怎么问、得到什么才有用”，再决定工具和文件。

`skill-builder` 负责产品定义；`skill-creator` 负责 Skill 包结构、frontmatter、渐进披露、资源组织、静态校验和工程评测。

Skill 不是对任务步骤的重复描述。它应当纠正一种稳定、可观察的行为缺口，或把一项有明确契约的操作能力可靠地提供给 Agent。设计时先确认这项存在理由，再决定需要多少方法、原则和资源。

## 1. 扮演真实使用者

结合当前对话、已有工作流和实际业务，写出 5-10 个用户真的会提出的问题。覆盖：

- 需要立刻采取行动的问题。
- 日常或周期性复查的问题。
- 异常、缺失数据和失败场景。
- 会暴露职责边界或相邻 Skill 的问题。

问题使用自然语言表达结果诉求，例如“为什么这批任务没有执行”，而不是“调用队列查询工具”。优先从已有上下文推断，只有关键业务选择会改变职责时才向用户确认。

## 2. 判断是否需要设计意图层

每个 Skill 都要有可说明的存在理由，但最终正文不必统一增加“哲学”章节。先判断 Skill 的主要性质：

- **判断型 Skill**：Agent 需要在多个看似合理的动作之间取舍，容易为了产生结果而过度行动、停在表面现象或机械执行清单。
- **操作型 Skill**：主要价值是可靠执行一个确定性工具、数据或外部系统契约，核心风险来自权限、输入输出、副作用和失败处理。

判断型 Skill 在进入能力设计前明确：

1. 没有该 Skill 时，Agent 会稳定出现什么可观察的错误行为。
2. Skill 最终为用户优化什么结果；多个局部指标冲突时，哪个结果优先。
3. 面对多个可行方案时，哪些事实和取舍决定选择。
4. 什么证据表示任务已经充分完成；何时不修改、不新增、不提出问题或不继续调查也是正确结果。

操作型 Skill 用一句话说明为什么需要这项专门能力，并把重点放在准确契约。只有操作中存在真实判断分支时，才补充对应的取舍和停止条件。

优先从用户反馈、失败记录、实际执行轨迹和相邻 Skill 的冲突中寻找行为依据。避免使用“更专业”“更高质量”一类无法观察和验收的理由。

## 3. 映射问题到能力

为每组问题确认：

1. 用户最终需要知道、决定或完成什么。
2. 哪些事实、文件、数据或运行状态可以支撑答案。
3. 最小必要动作是什么：读取、查询、转换、生成、修改或调用外部服务。
4. 哪些判断由 Agent 结合证据完成，哪些步骤适合确定性脚本。
5. 成功、数据缺失、权限不足和外部失败时应返回什么。

工具服务于问题。一个稳定问题簇对应一项能力；同一个工具可以支持多个问题，不需要把数据源的每个接口都包装成能力。

## 4. 划定产品边界

用一句话命名 Skill 的稳定职责，并检查：

- 各问题是否属于同一用户目标和决策上下文。
- 是否与现有 Skill 重复，应该扩展、组合还是新建。
- 默认值、环境范围、数据安全和失败边界是否明确。
- 哪些功能缺口应留给其他 Skill 或后续版本。
- Skill 是否在输出原始信息之外，帮助用户完成真实任务。

当职责无法用一句话说清时，重新分组问题，而不是创建一个无边界的通用 Skill。

## 5. 产出 Skill Brief

在写文件前形成简短的实现输入：

```markdown
# Skill Brief

## User questions
用户会提出的代表性问题。

## Responsibility
Skill 承担的单一稳定职责。

## Design intent
判断型 Skill 记录需要纠正的默认行为、优化结果、关键取舍和正确停止方式；操作型 Skill 只记录必要的存在理由，确实没有额外判断时省略其余内容。

## Evidence and actions
每类问题需要的事实来源、工具和最小动作。

## Answer contract
用户最终得到的结果、关键字段和失败表达。

## Boundaries
默认值、安全限制、不负责内容和相邻 Skill。

## Acceptance scenarios
3-5 个真实问题及预期可观察结果。
```

这个 Brief 是产品设计结果，不是 API 清单或实现方案。`Design intent` 约束最终行为，不要求 `SKILL.md` 原样保留标题或措辞；实现可以把它融入目标、决策顺序、资源路由、输出契约和验收场景。

## 6. 交给 Skill Creator 实现

完成 Brief 后读取并遵循 `skill-creator`。由它决定：

- Skill 放置位置和重名处理。
- `SKILL.md`、`scripts/`、`references/`、`assets/` 和 `agents/` 的结构。
- description 的触发边界和正文的渐进披露。
- 静态校验、Fresh Agent 测试及是否需要高级评测。

把 Brief 作为实现和审查的验收依据，不在 Builder 中重复工程规范。

## 7. 产品验收

实现后重新使用最初的真实问题：

- Agent 是否选择了正确 Skill 和能力。
- 答案是否解决用户问题，而不只是描述数据或工具输出。
- 缺失数据和失败情况是否仍然可行动。
- 新增能力是否仍属于已定义职责。
- 常见任务是否比没有 Skill 时更稳定、更省上下文或更少返工。
- 判断型 Skill 是否改变了目标行为，而不只是增加一段理念说明。
- 判断型 Skill 是否包含至少一个“准确地不做更多”场景，并在结果充分时停止。
- 操作型 Skill 是否仍保持简洁，没有因统一模板增加无关判断和上下文。

发现缺口时先更新问题地图和 Brief，再调整实现，避免围绕单个测试样例追加特例。
