# 编写与重整规则文档

本页用于个人或项目的 `AGENTS.md`、`CLAUDE.md` 及相应规则文档。沿当前环境实际的发现与适用范围核实行为，必要时查对应产品的官方说明。

## 先还原规则的效力

通读当前规则及被引用资料，将内容按作用归类：

- 持续生效的个人偏好和协作要求。
- 用户保留的决策权、授权条件和执行边界。
- 项目或目录拥有的业务、技术与运行约束。
- 只在某类任务中使用的具体方法。
- 可从已有配置、代码或命令核实的事实。

区分规则的效力、适用范围与详细解释。比如“数据变更需要明确确认”涉及谁有权作决定；比较复用方案和列出使用方影响，则说明怎样准备一个可审阅方案。精简时分别安排它们的归属。

## 选择常驻内容

保留跨任务需要、需要尽早影响行动或遗漏后果较大的短规则。把详细方法放到已有职责所有者，通过明确条件取得。

个人偏好按用户实际要求保留。下列变化需要作为行为变化明确处理：

- 把明确确认改成代理自行判断。
- 把必须遵守的约束改成一般建议。
- 缩小数据、环境或任务的覆盖范围。
- 让原本持续生效的规则依赖一个尚不可靠的入口。

例如，原规则覆盖字段含义和既有 JSON 中的新持久化结构，候选仍须表达这两项。只写“数据库迁移先确认”会丢失一部分适用范围。

## 用已有所有者承接详细方法

迁移一项内容前，读取接收材料并确认它已经表达相同语义。仅有相似主题时，保留当前短规则，或在授权范围内补齐接收位置。

常驻入口说明“什么任务使用哪种方法”，如修改业务代码时使用实现方法，涉及公共 API 或生命周期时使用架构方法。具体的偏好强度仍由有效规则决定。

整理时为重要规则记录去向：留在候选何处、已有哪份材料完整承接、哪些仍缺少接收位置。这份映射供审阅使用，按任务文档归属保存。

同一要求多处出现时，合并为一个完整规则，其他位置引用它。把表达相同的范围约束和主动推进要求合起来，使 AI 同时知道应完成什么、何时需要重新确定范围。

## 复查候选

从原始要求逐项核对候选：

1. 用户原有的决策权、偏好强度和适用范围是否保持。
2. 详细方法是否有真实接收位置，入口条件是否清楚。
3. 新的措辞是否引入额外审批、执行步骤或长期责任。
4. 每个章节是否聚焦一个职责，是否仍有重复或冲突。

用户要求平行候选时，将状态与评阅说明放在候选外部；候选正文表达将来实际要执行的规则。采用前保留现有规则、链接和发现配置。
