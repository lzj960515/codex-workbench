# Verification Before Completion

## 目标

让每个完成声明都对应最新、可见且范围匹配的证据，不把局部检查包装成整体成功。

## 执行流程

1. 列出即将做出的关键声明，例如原始 Bug 消失、目标测试通过、构建成功、仅修改预期文件。
2. 为每条声明选择成本最低但真正有证明力的检查。按改动风险组合定向测试、集成测试、类型检查、lint、构建、格式检查和运行时验证。
3. 在最后一次相关代码修改后运行检查。读取退出码和关键输出；代理摘要、旧日志或“应该通过”不算新证据。
4. 检查最终 diff、未跟踪文件、暂存范围和工作树状态，确认没有遗漏、意外产物或用户无关改动。
5. 评估 warning、open handle、重试、跳过测试和环境依赖是否削弱结论。必要时追加检查，或缩小完成声明的范围。
6. 提交、推送、PR 或发布前核对当前分支、目标仓库和远端结果。只有命令成功后才报告对应动作完成。

## 风险缩放

- 小型文档或机械改动可用内容检查、格式和 diff 证明。
- 共享库、公共 API、持久化、队列和跨模块行为需要定向测试及更广回归。
- 无法执行完整验证时，清楚列出已运行检查、未运行检查、原因和剩余风险；继续完成用户明确允许的动作。

## 输出方式

简洁报告验证命令对应的结果和范围。测试失败、被跳过或仍在运行时，不宣称通过；部分验证只支持部分结论。
