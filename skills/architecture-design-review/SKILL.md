# Architecture Design Review

## 目标

为已经确认的能力建立完整且一致的系统模型，让它自然落入稳定抽象，同时保持产品责任和实现范围与当前目标一致。讨论尚未确认的方向时，先比较目标与取舍；目标确认后，架构设计负责实现它所需的完整职责边界。

完整模型用于看清当前能力在系统中的所有影响，不代表把每一种可能的扩展都建设出来。每个新增公共接口、状态、持久化、调度、恢复、兼容机制和抽象都应由当前目标、既有契约、已证实风险或已知 Roadmap 中当前阶段需要的职责接缝支撑。缺少某项能力会使当前验收失败时，它属于完整模型；只会改善体验、增加通用性或服务未来复用时，它仍是候选方向。完整生命周期检查负责发现需要核实的问题，当前系统证据负责决定哪些机制进入实现。

架构设计可以确定实现已确认行为所需的内部职责，不替产品决定新的用户交互、支持平台和运行承诺。现有系统的关键代码、契约或环境事实不可用时，把组件形态和技术选择保留为待证实方案；用户明确要求从零设计时，才基于标明的假设形成绿色项目模型。

## 工作方式

1. 明确当前是在比较候选方向还是设计已确认目标；分开写出已经确认的用户可见结果、由当前证据证明的必要系统行为、现有契约、证据尚未决定的事项和不属于当前阶段的候选能力。
2. 阅读与问题相关的完整路径：公共类型、调用链、模块装配、持久化、测试、文档和运行时边界。已有成熟框架时，同时核对其原生术语与生命周期。
3. 用简短模型明确稳定概念、所有权、生命周期、状态边界和不变量，区分当前目标要求的行为、长期稳定的职责接缝和未来候选能力。
4. 按生命周期归类当前需要的数据：定义期固定规则用 `Config`，实例创建参数沿用宿主框架命名，调用期可变参数用 `Options`，运行中数据使用明确的 State 或 Context。
5. 检查职责归属。每个类承担一个稳定且可命名的职责；无处自然安放的代码通常意味着职责边界或抽象仍不完整。重复出现的状态机、协调协议或收尾逻辑优先收敛为共同机制。
6. 从使用者视角审查公共 API。设计或重划模块接口、依赖位置与测试边界时，读取 [Codebase Design](references/codebase-design.md)，判断封装隐藏了哪些复杂性、调用者需要掌握哪些契约，以及变化是否集中在真实职责所有者。保持类型推断和领域意图；本 Skill 的生命周期与范围约束共同决定设计。
7. 检查当前能力的完整运行模型：成功、失败、重试、幂等、多实例、恢复、持久化、可观测性和兼容性。只针对真实风险增加复杂度，只保留当前阶段需要的稳定职责接缝，把未来能力本身留作候选。
8. 将发现分类为确定 Bug、一致性问题、功能缺口、业务模型问题或架构债务。一起处理当前目标需要、同根因且风险可控的问题，其余形成明确的后续边界。

## 输出与实施

- 设计讨论先给推荐模型、关键取舍和被否决方案的实质原因。
- 已确认目标的实施方案说明当前必须建设的职责、仍需证据决定的技术与交互、保留的稳定接缝和未纳入实现的候选能力。
- 代码审查先列具体问题和位置，再说明整体职责或数据流问题。
- 实施时让改动融入现有结构，并补齐与风险相称的测试和文档。
- 小型且模式明确的改动保持轻量；无需为了使用本 Skill 强制创建设计文档、worktree、子代理或额外审批阶段。
