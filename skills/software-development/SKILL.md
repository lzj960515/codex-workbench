# 软件开发

从真实业务目标、现有契约和使用场景理解代码，选择适合业务且总体责任清楚的模型与技术，把完整行为实现于其所属位置。以必要的验证和独立审查完成交付。

业务决定要保证什么，职责与生命周期决定代码放在哪里，运行证据说明实现是否成立。模型的简单程度按概念、状态、分支、迁移、兼容与长期维护的总体成本判断；代码量和采用的技术本身不作为优劣标准。

## 按当前任务进入

| 任务 | 工作范围 |
| --- | --- |
| 实现功能、修复已定位问题或实施重构 | 完成下文开发流程 |
| 只设计或比较架构 | 理解目标与现状，按需设计，交付推荐、依据和未决事项 |
| 只审查代码、分支或合并请求 | 直接按 [审查方法](references/review.md) 独立判断并给出结论 |
| 处理审查意见 | 核实意见，完成获授权的修复或回复；有代码修改时按开发流程收尾，优先由原独立审查者复审 |
| 只编写或调整业务测试 | 按 [测试选择](references/testing.md) 保护已确认行为，完成测试代码的验证与独立审查 |

从当前请求和已有进展继续，复用已经明确的目标与证据。设计、只审查和反馈回复各有自己的完成结果。需要诊断未知根因时，使用 `systematic-debugging` 建立因果依据，再将确认需要修改的代码交回本流程。项目与框架专用能力补充具体契约。

## 1. 明确业务结果与执行边界

从一个真实请求或使用场景说明谁做什么、当前结果和所需变化。基础设施以调用方契约表达结果，例如取消任务后释放资源、请求结束后状态不串到其他请求。

通读目标代码、相关说明和引用资源，沿受影响的入口、写入、处理与使用方理解完整路径；按实际影响追踪展示、恢复、同类实现与框架生命周期。调查深度与改变结论所需的证据相称。

区分已确认目标、现有契约、必要行为与候选增强。每项新增行为、依赖、状态、兼容路径和运行责任都应能说明为何是完成当前目标所必需。关键事实不可用时，保留依赖它们的决定并说明缺口。

模型选择遵循适用规则中的数据变更授权：先比较复用现有模型能否完整满足结果，再提出必要的新模型；具体数据变更获明确确认后开始依赖它的实现。测试与代理方案不构成需求或授权。

## 2. 确定模型、职责与实现规模

先找现有模型、领域动作、共享能力与已有依赖。根据输入输出、数据所有权、生命周期和失败结果，确定行为应归入哪个职责。普通方法已经能完整承载时直接实现；真实职责或生命周期需要分开时，再调整边界。

比较方案时关注完整结果与总体责任：为什么需要独立保存一个事实，新增状态由谁写、谁读、何时失效，既有处理链路具体哪里不足。根据实际项目条件选择成熟框架、已有库或小型实现。

公共 API、共享状态、新生命周期或跨模块职责发生变化，以及复用、代码位置和异常边界难以判断时，读取 [设计与实现](references/design-and-implementation.md)。沿用框架原生概念，先判断实际边界，再选择抽象和模式。

## 3. 先确定怎样证明结果

从已确认业务结果、现有契约与真实缺陷选择代表场景和重要边界，再选择验证方式：

- 已有检查充分覆盖时复用；机械接线和框架接入使用能够直接证明结果的源码核对、类型检查、构建或目标调用。
- 项目自己拥有的业务规则、重要边界与真实缺陷需要回归保护时，新增有价值的自动化测试。
- 新增行为或修复缺陷需要测试保护时，先写能暴露目标缺口的用例，确认失败原因后实现；为已有正确行为补充测试时核对当前契约。用户明确要求 TDD 时按该方法推进。

测试关注真实业务结果。框架默认行为、配置透传与注入接线按项目约定直接验证。判断是否需要测试时考虑业务后果：金额、权限和租户隔离可能只有一条判断，也可能承担重要契约。

需要选择测试边界、处理输入校验、安排 TDD 或遗留代码验证时，读取 [测试选择](references/testing.md)。生产设计以业务和运行需要为依据，测试替身与准备留在测试侧。

## 4. 实现清楚的业务主流程

让入口按业务顺序表达动作。高层方法保持同一抽象层级，名称说明领域意图；转换、技术调用与分支细节归入职责明确的方法或对象。类型、注释和模块位置帮助读者理解契约与必要原因。

按真实输入、明确契约和可信的重要风险决定保护措施。让异常沿既有边界传播，在能恢复、转换错误、释放资源或补充必要上下文的位置处理。部分成功及失败容忍度遵循已确认语义。

替换现有职责时，切换真实使用方并核实旧路径退出；有兼容需要的路径保留具体依据和退出条件。扫描同根因、同契约且当前需要的受影响位置，其他问题留下清楚的后续边界。

读完从任务原始基线到当前结果的完整差异，核对新增文件、调用方、暂存与未暂存修改。确认目标、职责、业务顺序及所需检查已明确，再进入独立审查。

## 5. 主动完成独立审查

每次形成一组可交付的代码改动后，由负责实现的主 Agent 主动启动一位独立审查子 Agent，使用 [审查者说明](agents/reviewer.md) 与 [审查方法](references/review.md)。局部改动保持审查范围和交付简洁；同批代码的连续编辑与修复复用这一审查过程。

交给审查者：原始用户目标、已确认决定与授权、项目位置、任务基线、完整改动范围，以及实际验证结果和未验证部分。让审查者从代码与契约独立判断，区分事实、实现者方案与尚待核实的解释。

主 Agent 完成与变化相称的检查，审查者复用证据并调查会影响结论的疑点。审查应同时检查业务正确性、模型必要性、职责归属与多余的设计、防御和测试；准确批准是完整结果。

审查者的职责是给出独立判断与证据，保持只读并直接返回结论。只审查任务完成于这份判断，由实现主 Agent 组织后续处理。

## 6. 收敛问题并交付

逐项核实审查意见：成立的在授权内修复，不适用的说明代码或契约依据，需要改变已确认边界的交回用户决定。修复后验证受影响行为，优先让原审查者复核原问题、修正及其影响。

再次审查服务于新的差异或尚未解决的重要疑点。原阻塞已解决、验证充分且没有新阻塞时结束；保持判断依据，避免为产生更多意见反复展开全面审查。

按 [交付与证据](references/delivery.md) 核对最终状态，复用仍然有效的直接证据，只补受新变化影响或尚未证明的部分。报告完成结果、独立审查结论、必要验证和仍有影响的边界。

用户明确要求跳过某项检查或独立审查时，遵循本轮要求并说明实际状态。工具不可用或审查未完成时，明确保留“未完成独立审查”的状态。提交、推送、发布与生产操作按当前授权和对应流程执行。
