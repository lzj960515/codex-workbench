# 独立审查与反馈收敛

代码审查判断候选是否忠实完成业务目标、适合交付，并推动真实问题得到解决。准确批准与准确退回具有同等价值；问题数量和审查轮数不作为质量标准。

## 实现完成后主动安排初审

每个完整可交付的代码变更完成必要验证后，由实现主 Agent 主动启动独立子 Agent，使用[审查者角色](../agents/reviewer.md)，无需用户提醒。同一批实现的持续编辑不按每次保存、每个文件或每次修改重复初审。

交接提供原始用户目标与约束、已确认事实和决定、授权范围、原始基线、完整任务差异，以及已执行检查的实际结果与证据位置。区分用户要求、代理推荐和未决事项。审查者自行读取适用规则、业务契约、相关入口和使用方，独立核实实现者的解释。

用户明确要求跳过审查时遵循要求并说明状态；独立工具不可用时，如实交代尚未完成独立审查，现有自查只能按自查报告。任务只要求设计或只审查候选时，在相应工作完成后结束；处理反馈按下文核实与复审，不从头重走整套实现流程。

## 从业务与职责检查候选

先从原始目标核对方案必要性和授权，再检查正确性。沿本次改动的真实路径理解入口、写入、处理、使用、展示与恢复，按影响读取同类实现、测试及运行证据。

审查模型能否用更简单且完整的现有职责承载，技术是否适合当前业务，新增状态、抽象、防御、兼容路径和运行责任是否有依据。类与模块要表达稳定职责，主流程让后续读者容易理解；名称或模式偏好本身不足以否定实现。

替换职责时核实真实调用方已经切换，旧路径已经退出，或仍有具体消费者和退出条件支撑临时共存。区分当前变更引入的问题、目标所需的修复和范围之外的相邻问题。

测试同时接受必要性审查：它应保护业务结果或已证实缺陷，而不是镜像实现、验证框架默认行为，或迫使生产代码增加只为测试存在的接口与分支。测试全绿不证明目标、模型和授权正确，也不证明尚未覆盖的业务边界安全。

## 以证据决定哪些问题阻止交付

把疑点还原为具体的交付影响，再决定是否要求修改：

- **行为问题**：说明谁通过哪个受支持入口执行什么动作，什么输入或状态触发当前代码，预期与实际业务结果如何不同。以完整调用链、已有测试或必要的最小检查支持结论。
- **模型、职责与范围问题**：对照已确认目标和现有可行方案，指出额外责任、重复事实来源、未退出的旧职责或不必要防御造成的维护与业务影响。
- **授权问题**：列出实际变更与用户批准范围的具体差异；测试和候选方案不能代替用户确认。

行为问题使用一个最小真实例子解释。并发问题还原真实生产者的交错顺序；必要性和授权问题直接引用目标、契约与差异，无需另造运行故障。

代码层面可构造的状态只是调查线索。内部函数不会接收的非法输入、缺少现实后果的想象异常和一般惯例，先核实其真实适用性。真实入口能够接收的输入确实会触发错误、核心不变量受损或重大风险具有可信触发条件时，保留必要保护。

只把会改变当前交付判断、具有充分证据的问题列为阻塞。能够批准时直接批准；仍缺决定性证据时说明具体缺口和它限制了哪项结论。已有证据足够时复用，真实疑点才补充成本最低的必要检查，不从头重跑全部测试。

## 主 Agent 核实并处理意见

审查意见是需要判断的结论，不自动成为需求。主 Agent 阅读对应代码、调用链、业务契约和证据，分别决定：

- **修改**：问题成立且在当前授权范围内，完成修复，扫描同根因位置，并运行受影响的必要检查。
- **回复**：意见与实际入口、既有契约或当前范围不符，给出具体依据；不为取得同意增加无依据的能力。
- **请求产品决定**：成立的问题需要实质改变已确认业务、数据、安全或兼容范围，先形成具体取舍与可审阅方案。

用户纠正方案时，从任务原始基线检查完整差异，清除被否定假设形成的产物。已有实现投入与测试断言不构成保留错误方案的理由。

## 对修改复审并结束

将修复内容、对意见的回复和新增证据交给原审查者，优先核对原阻塞、受影响位置与契约，以及修复是否引入新的真实问题。只有新的重大差异或实质证据改变范围时，才扩大检查；相同材料下不反复开展全面审查。

审查者根据反证更新判断，成立的修复确认关闭，不适用的问题明确撤回。主 Agent 对仍有分歧的意见核实业务与证据，按现有契约作出判断；需要用户决定的实质取舍单独提出。不以不断新增审查者寻求一致意见。

已成立阻塞解决、受影响结果有充分证据且没有新的交付阻塞时，结束本批审查并交付。新的代码变更使此前结论不再覆盖最终产物时，补足受影响部分的验证与复审，不按固定轮数跳过真实问题。

报告先给出能否交付的结论，再提供必要依据。存在阻塞时按影响排列，每项说明业务后果、证据位置与处理方向；批准时说明检查范围和证据边界。明确区分独立审查、自查、尚未审查与用户要求跳过的状态。
