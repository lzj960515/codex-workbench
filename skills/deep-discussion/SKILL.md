# Deep Discussion

## 稳定职责

与用户共同分析尚未确认的想法、比较候选方向并形成证据充分、可执行的判断，再让讨论结果进入与其后续生命周期相称的载体。

让用户清楚这一轮在讨论什么、自己的回答会帮助确定什么，以及下一步由谁推进。讨论的进展体现在共同理解和决定发生了什么变化。

讨论深度和文档形式都服务于当前问题。用判断选择它们，不把深入讨论变成固定辩论流程，也不把文档当作每次讨论的必需产物。

讨论阶段负责判断一个目标现在是否值得做、应该怎样定义以及哪些方向应当暂缓。用户确认目标或明确进入实施后，把已确认的用户可见结果和产品约束作为执行阶段的范围输入；实现所需的职责边界由对应实施 Skill 处理。

## 开始讨论

1. 区分用户此刻是在探索想法、比较方向、形成决定，还是推进已经确认的目标，并明确当前任务授权了哪些读取、修改和外部动作。
2. 阅读用户提供的材料。涉及项目时，从目标位置向上读取适用的 `AGENTS.md`，再阅读相关代码、文档、运行事实和已有讨论稿。
3. 还原当前状态：已经确认的事实与决定、仍在使用的假设、证据缺口和可选方向，确定这一轮要弄清楚的具体问题。
4. 先回应用户本轮的问题和反馈，再选择能推进当前问题的动作：直接回答、补充调查、共同推敲一个取舍，或推进方案并维护文档。
5. 完成当前范围内可以自主完成的动作；把实现、发布、外部写入和项目状态变化交给当前任务授权及相应专门工作流。

当用户已经确认目标并要求形成执行边界时，按这个顺序收敛：

1. 写出用户明确确认的可观察结果和产品约束。
2. 从当前代码、测试、产品契约和已定位根因中确认实现该结果所必需的职责。
3. 把证据尚未决定的用户交互、支持范围、数据处理和运行机制保留为未决事项。
4. 把只会改善体验、增加通用性或服务未来复用的内容保留为候选方向。

宽泛的目标动词表达用户意图，不等于一份常见功能清单。行业惯例和相邻产品能力用于寻找需要核实的问题，当前证据和用户决定负责把具体能力纳入范围。

执行边界负责把已确认目标变成可进入实现的范围，不把一句结果目标扩写成完整产品规格。验收条件逐项对应已经确认的行为和必要机制；常见的附属交互和支持承诺继续作为候选，直到用户决定或当前产品契约已经拥有它们。

## 调整思考深度

结合以下维度判断它们会不会实质改变结论：

- 问题本身的复杂度与未知程度；
- 决定的影响、可逆性和错误代价；
- 当前证据是否直接、完整且仍然有效；
- 结论是否会进入后续实施、验收、长期维护或多人协作。

据此选择合适深度：

- **直接回答**：事实充分、结论明确、影响有限时，先给结论和必要依据。
- **重点核实**：存在少量决定性假设时，调查这些假设并说明它们怎样影响选择。
- **深入推演**：高影响、跨边界或长期方案需要建立完整模型时，读取 [决策树追问](references/grilling.md)，围绕目标、约束、证据、候选方向、失败方式和后续生命周期推进当前可讨论的决定。

只检验会改变结论的反证与风险。区分足以否定方案的问题、需要保留的约束和普通实现细节。已有方案与证据一致时，明确说明为什么成立，然后继续推进；只有替代方向会带来实质不同的结果时才展开比较。

## 取得证据与澄清

优先从当前范围内可读取的来源取得答案：项目文档、代码、类型、测试、Git、配置、运行状态或用户已给出的事实。区分：

- 已核实事实及其来源与时效；
- 从事实推导出的判断；
- 为继续推进暂时采用的工作假设；
- 仍需用户或外部来源确认的未知项。

把讨论中提出的功能、方案和扩展方向视为候选判断，结合核心目标和证据说明支持、反对、暂缓或缩小它们的理由。把用户已经确认的决定、当前证据证明缺少就无法得到结果的必要行为，以及只会改善体验或未来复用的候选能力分开记录，避免候选方向在后续实施中被误当成需求。

需要向掌握信息的其他人收集答案以推进当前决定时，读取[对外确认问卷](references/questionnaire.md)，整理对方能回答的信息缺口。

证据已经支持结论时直接推进。非阻塞缺口可以作为明确标记的假设保留，并说明验证时点。

讨论涉及业务术语歧义、概念关系或需要保存重要取舍时，读取 [领域澄清与决策记录](references/domain-modeling.md)，用既有词汇和具体场景检验模型，并按下文文档所有权保存结果。

## 让讨论能够接下去

把自己的判断与当前要共同弄清楚的问题连起来。用户的回答、例子和异议用于修正理解、深入关键处或转入下一个未决事项；讨论仍围绕已确认的目标展开。

根据当前问题安排参与方式：

- **需要用户的经验、偏好或取舍**：说明现在想了解的具体事情，以及答案会影响什么，再提出用户能够回应的问题。方案选择可以给出推荐及代价；了解经历或意图时邀请具体例子。问题的意义应从眼前场景看得出来。
- **需要查证现有材料**：由 Agent 在已有授权内完成调查，清楚说明自己要查什么、用于判断什么，再带着结果推进讨论。独立于调查结果的用户问题可以同时讨论。
- **当前问题已有充分结论**：说明结论、依据和仍有影响的不确定性，完成已有授权内的后续动作；本轮只要求讨论或答复时，在交付结论后收束。

让问题的数量和形式服从当前决定之间的依赖：优先讨论已经具备前提的关键问题，相互依赖的取舍随回答逐步展开。已确认的决定作为后续讨论的依据，新的提问用于补充真正影响理解的部分。

例如，讨论导入失败的处理时，可以说：“停止整批便于一次核对完整性，继续导入则能先用上有效资料。你们遇到少数坏记录时，更在意哪一个结果？”需要核对现有行为时，则说：“我会查导入代码和失败记录，确认当前是否会留下部分数据，再据此判断方案。”两种表达都让参与者知道这一轮要解决什么、谁来提供下一步依据。

## 选择直接回复或文档

把下面信号作为校准依据，结合它们作整体判断，不做机械计分。

直接回复通常适合：

- 一次交流可以完整说明；
- 影响有限且容易修正；
- 事实和边界已经足够清楚；
- 结论没有独立的实施、交接或维护生命周期。

持续文档通常适合：

- 讨论需要跨会话继续或预计反复修订；
- 结论将指导后续实施、分阶段推进或验收；
- 多个 Agent 或协作者需要从同一状态继续；
- 多项依赖、决定和未决事项需要保持一致；
- 上下文压缩后仍需准确恢复当前结论与下一步。

比较遗忘、误解和重复讨论的成本与维护文档的成本。深入讨论本身不必然产生文件；简短问题也可能因为后续交接而需要持久化。

当事项需要跨会话选择和推进多个相互依赖的决定，或正在恢复一份决策地图时，使用 `wayfinder` Skill，由地图管理当前可推进事项。单个问题的深入讨论继续使用本 Skill。

当已形成的决定需要整理为指导实施、交接或验收的正式规格时，使用 `to-spec` Skill，传递已有讨论、决策记录和文档所有权；普通讨论继续使用与其生命周期相称的载体。

## 确定文档所有权

需要持久化时按以下顺序确定载体：

1. 按适用的 `AGENTS.md` 确认文档目录、所有权和 `tmp/` 状态文件约定。
2. 搜索同一主题已有的讨论稿、方案、任务状态文件和权威项目文档。
3. 已有讨论产物能够承载本次变化时，持续更新同一文件。已采用决策地图时，把当前问题的依据与结论记录在对应事项中，地图只保留摘要链接；下文讨论稿结构用于尚未采用地图的讨论。
4. 没有合适载体时，创建满足当前讨论所需的最小文档。项目没有另行约定时，使用 `tmp/YYYY-MM-DD-<topic>-discussion.md`。
5. 结论进入实施或长期维护后，把已确认内容更新到最接近其所有者的现有权威文档，让讨论稿记录状态并指向该来源。

每个事实只保留一个当前权威来源。讨论稿负责形成和恢复方案，权威项目文档负责已经确认并进入项目生命周期的事实。

## 维护一份持续演进的讨论稿

新建文档默认标记为“讨论稿”。根据内容保留下面最小结构，省略当前不需要的空章节：

```markdown
# <主题>

- 状态：讨论稿 | 已确认方案 | 已被取代
- 文档职责：说明本文件承载的讨论范围
- 权威来源：尚无 | <项目文档路径>
- 最后更新：YYYY-MM-DD

## 目标与范围

## 当前结论

## 依据与工作假设

## 未决事项

## 下一步

## 变更记录
```

维护时执行这些动作：

- 就地修订“当前结论”，让读者首先看到现在仍然成立的方案。
- 分开记录已确认决定、候选判断和工作假设；为关键事实保留来源或可复核位置。
- 将已经解决的问题移出“未决事项”，把被取代的结论从当前正文移入简短变更记录。
- 每轮结束前更新下一步，使另一个 Agent 无需聊天摘要即可继续。
- 只记录有助于恢复或解释决定的实质变化，保持文档可读。

用户明确确认或项目既定审批流程确认后，才把候选决定标记为“已确认”。如果目标项目已有承载该事实的权威文档，把确认内容写入该文档，并在讨论稿中记录链接与迁移状态。项目约定讨论稿本身拥有该主题时，它可以按约定成为权威来源。

## 从文档恢复讨论

新会话、上下文压缩或 Agent 交接后：

1. 读取适用的 `AGENTS.md`、指定讨论文档及其引用的权威来源。
2. 提取当前结论、已确认决定、工作假设、未决事项和明确下一步。
3. 对 Git、代码、配置、运行状态等可能变化的事实做范围相称的复核。
4. 简短说明恢复到的状态，然后从文档中的下一步继续。

文档与当前事实冲突时，以可核实的新事实修订当前结论，并记录这次变化。存在多个可能的当前讨论稿且所有权无法判断时，列出差异并询问一个决定所有权的问题。

## 交付结果

直接回复时：

- 先回答用户本轮的问题，给出当前判断及其依据；
- 说明真正影响后续决定的约束和未决事项；
- 仍需共同讨论时，落到本轮需要用户回应的具体问题；后续属于 Agent 的调查或执行时，说明动作并在已有授权内推进；
- 内容在对话中已经完整闭环时，不创建文件。

创建或更新文档时：

- 说明文件路径和当前状态；
- 概括本轮改变的结论、依据或未决事项；
- 指出权威来源和下一步由谁推进、解决什么；需要用户参与时在回复中提出具体问题；
- 让最终回复保持简洁，完整方案由同一文档承载。
