# 按业务结果选择测试与验证

在决定新增测试、复用已有用例或直接验证时读取本页。测试保护已确认的业务结果、既有契约和已证实的缺陷；验证方式按真实风险选择。

## 先确定需要证明的行为

从本次业务动作识别输入、可观察结果、数据与外部副作用，以及必须保持的不变量。核实现有入口、调用方与测试，确定当前证据还缺什么。

业务分支、金额计算、状态转换、持久化、重试、并发、权限和租户隔离值得重点检查，但这些分类本身不要求增加用例。已有测试能够保护受影响行为时，运行相关用例即可；存在真实回归缺口时，再补充能够发现该问题的测试。

简单程度不能代替业务判断。例如：

- 将一个配置名改为另一个配置名，可以通过差异核对、配置渲染或目标启动证明结果。
- 一行店铺过滤决定能否读取其他店铺的私密记录，需要保护跨店访问的业务结果。
- 内部函数只接收公开入口已经验证的枚举值时，按这条真实调用契约验证；公开接口接收付款金额时，核对真实输入如何影响扣款和拒绝条件。

测试从支持的入口和实际生产者构造场景。业务边界、已发生缺陷和有可信触发条件的重大风险形成验证依据；仅能通过绕过契约、手工破坏内部状态构造的情况，先核实其可达性与业务影响。

## 选择充分且成本合适的方式

- **运行已有测试**：已有用例覆盖本次需要保持的业务行为，或能够验证等价重构。
- **新增测试**：现有验证缺少对项目自有规则、真实失败机制或重要契约的回归保护。选择能发现目标错误、又容易维护的业务边界。
- **直接验证**：机械接线、命名与类型调整、简单配置或一对一映射，可由完整差异、构建、类型检查、配置渲染或目标调用充分证明。

选择后执行必要检查，读取实际结果。每项新增检查对应尚未证明的结果或真实疑点；证据充分时结束，不为每个文件、方法、入参和配置项补齐形式上的测试。

框架默认行为、并发配置、依赖注入、装饰器接线和配置透传通过源码核对、构建和实际运行检查验证，禁止为这些内容编写框架层面的测试。项目自己的并发业务规则仍按业务结果验证，例如重复付款是否受既有契约约束。

## 让测试独立证明业务契约

通过公开行为和稳定接口观察结果。期望值来自已确认需求、既有契约或缺陷事实；避免在测试中复制生产算法、断言私有方法或排列 Mock 调用来重复实现。调用顺序本身影响业务语义时，才将必要顺序纳入断言。

使用项目已有的数据准备、外部边界替身和受控本地依赖。核心规则由真实实现执行；跨模块协作、真实存储或队列语义需要相应边界的证据，不能靠 Mock 掉被验证职责来证明。

Bug 回归用例应在旧实现上因同一缺陷失败，并在修复后通过。重构用例锁定需要保持的行为；用户已确认替换旧职责时，同步整理失去业务依据的旧用例。

测试的目标与输入范围来自业务。尚未确认的支持方式、持久化结构、恢复机制和异常分支保留为待定方案，不能因写入测试断言而成为新需求。

## 需要 TDD 时

用户明确要求 TDD 或先写测试时，遵循失败测试到通过的顺序；其他任务按已选验证方式推进。采用 TDD 时：

1. 以业务契约写出最小有效用例，运行并确认它因缺少目标行为而失败。
2. 在真实职责所有者中实现所需行为，使定向用例通过。
3. 整理职责、命名与重复代码，保持行为不变，再运行与影响相称的回归检查。

失败应暴露目标问题；编译错误、环境不可用或数据准备失败不构成目标行为已经被测试证明的证据。报告实际失败原因、通过结果和回归范围。

## 保持生产设计的独立性

生产依赖、接口与行为由真实业务和运行生命周期决定。必需依赖保持必需注入，测试替身、数据准备和等待逻辑留在测试侧。禁止仅为测试便利增加可选依赖、默认空实现、测试开关、特殊分支、额外接口或抽象。

现有设计难以自动验证时，调整验证边界或使用直接检查；必要时减少、略去对应测试并准确说明证据范围。测试揭示真实业务缺陷时按事实修复，测试本身不构成新增生产能力的理由。

交付时简要说明选择了什么验证、实际执行了什么，以及证据尚未覆盖的业务边界。测试通过只证明被检查的性质，不替代需求方向、模型必要性与授权核对。
