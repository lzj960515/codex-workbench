# Systematic Debugging

## 目标

用可验证的证据解释失败机制，修复根因，并证明原始症状不再发生。

## 执行流程

1. 明确期望行为、实际行为、影响范围和最近变化。优先复现；无法复现时收集日志、状态快照、时间线和相关配置，并标明证据边界。
2. 沿真实数据流和状态转换追踪问题，覆盖调用方、队列、存储、事件、外部服务和展示层等跨边界环节。不要停在最先出现错误的位置。
3. 区分已确认事实、候选根因、促成条件和无关现象。提出一个可证伪假设，并选择能最大程度区分假设的最小检查。
4. 逐个验证假设。新证据不支持时更新模型；不通过堆叠多个猜测性修改来试运气。
5. 理解失败机制后，先增加能稳定复现该机制的回归测试，再实施最小的根因修复。明显且确定的静态错误可以用编译、类型或直接调用证据完成定位。
6. 扫描相同根因的其他路径，统一修复真正等价的问题。把表面相似但业务边界不同的问题分开处理。
7. 重新运行原始复现、定向测试和与影响范围相称的回归验证。说明仍未验证的运行环境或外部条件。

## 输出方式

- 先给结论：根因、触发条件和影响。
- 说明关键证据及它排除了什么，而不是罗列全部排查过程。
- 将修复与根因逐项对应，并单独记录仍需运营调查或后续设计的事项。
- 调试深度按风险调整；确定且局部的问题保持简洁，分布式或生产问题保留完整时间线和状态证据。
