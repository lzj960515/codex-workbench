# 系统化调试

## 职责

用当前证据建立能够解释异常现象的因果模型，给出与证据强度一致的诊断结论。当前请求包含修复时，在拥有根因的边界实施修复，并验证原始症状和失败机制已经消除。

这个 Skill 用来纠正“看到第一个异常位置就开始补代码”的默认行为。错误出现的位置可能只是后续症状；真正的原因可能属于上游业务规则、数据、配置、容量、部署版本、外部依赖或对期望行为的误解。调试的价值在于解释因果关系并指导正确动作，准确确认无需修改代码也是完整结果。

调查形成以下三种结论之一：

- **根因已确认**：证据能够解释触发条件、状态变化和可观察症状，并对主要竞争解释形成有效区分。
- **主要假设**：当前证据更支持一个解释，但仍缺少能够确认因果关系的关键检查。
- **证据不足**：现有事实无法可靠区分候选解释；明确缺少什么证据以及怎样取得它。

结论名称反映证据强度。诊断任务不以必须找到代码缺陷或产出补丁作为完成条件。

## 执行流程

1. **确认任务边界。** 区分“只诊断”和“诊断并修复”，确认允许读取和操作的环境。生产问题优先使用日志、指标、追踪、只读查询、状态快照和受控副本建立证据；运行写操作服从当前请求与对应系统的授权边界。
2. **定义异常。** 明确期望行为、实际行为、影响对象、发生频率、时间窗口、最后一次正常状态和最近变化。能够安全复现时记录最小复现；不能复现时保留时间线、输入、版本、配置和运行状态的证据边界。需要构造或改进复现、缩减输入，或选择诊断实验时，读取[复现与实验方法](references/diagnostic-experiments.md)，按当前证据缺口选择方法。
3. **比较正常与异常路径。** 选择健康请求、正常租户、成功任务、稳定版本或最小工作示例作为对照，比较输入、数据、配置、依赖、部署版本、时序和资源压力。优先检查能够解释两条路径差异的变化。
4. **追踪完整因果链。** 从业务入口沿数据流和状态转换向后追踪，也从症状位置向上游回溯，覆盖调用方、队列、存储、事件、外部服务和展示层。关键词搜索用于定位入口，调用链和生命周期决定根因归属。
5. **建立可证伪假设。** 分开记录已确认事实、候选根因、促成条件和无关现象。每次选择一个能够最大程度区分候选解释的最小检查，并尽量一次只改变一个变量。
6. **按证据收敛。** 新证据不支持当前假设时更新因果模型。证据达到确认标准时给出根因；仍缺决定性证据时给出主要假设或证据不足，不用猜测补全结论。
7. **在根因边界采取动作。** 只诊断任务停在可行动的诊断、恢复方向和待补证据。任务包含修复时，代码缺陷使用能复现失败机制的回归保护和最小根因修复；确定的静态错误可以用类型、编译或直接调用证据证明。数据、配置、容量和外部系统问题使用对应的恢复或调整动作。
8. **验证机制与影响范围。** 使用同一复现或同一类直接证据比较动作前后结果，再运行与影响相称的定向和回归检查。扫描同一根因的其他路径，统一处理业务语义等价的位置；独立现象另行调查。使用缩减复现修复后，重新验证原始完整场景；收尾时清理本次临时诊断日志和实验产物。

当当前范围已经形成与证据相称的结论，并且下一步动作或证据缺口清楚时结束调查。修复任务还需要确认根因对应的动作已经通过直接验证。继续排查只服务于仍会改变结论的重要假设。

## 输出方式

- 先标明结论状态：`根因已确认`、`主要假设` 或 `证据不足`。
- 说明期望行为、实际症状、触发条件、影响范围，以及关键证据支持或排除了什么。
- 将已执行动作与根因逐项对应；只诊断时给出下一项最有区分力的检查或恢复方向。
- 单独说明未验证的环境、外部条件和授权边界。局部确定问题保持简洁，分布式或生产问题保留必要时间线与状态证据。

## 与相邻 Skill 的边界

- `test-driven-development` 负责决定何时以及怎样建立回归测试。
- `maintainable-implementation` 负责把已确认根因转成可维护实现。
- `architecture-design-review` 负责根因暴露出的公共模型、框架或生命周期重构。
- `verification-before-completion` 负责最终修复声明与最新证据的对应关系。
- 具体运行恢复、生产写入和发布操作由相应系统的操作能力与授权流程负责。
