# Test-Driven Development

## 目标

把测试用在能够降低真实回归风险的位置。根据失败概率、影响、可观察性和测试维护成本决定是否新增测试；选择测试时，用可观察的业务行为证明需求和根因。

## 测试决策

1. 识别变更的业务影响、失败概率、发现难度和回滚成本，并确认现有测试、调用方和兼容约束。
2. 下面的变更优先新增测试：业务分支与计算规则、已发生 Bug 的稳定复现、公共 API 或事件契约、持久化与状态转换、重试与错误语义、并发与乱序、安全与权限、Store isolation，以及跨模块共享行为。
3. 下面的变更优先使用直接验证：简单配置源切换、环境或 Business Setting 接线、依赖注入和模块注册、常量与一对一映射、类型或命名调整、文档与生成产物，以及能由 build、typecheck、lint、配置渲染或调用检查完整证明的机械修改。
4. 测试只有在保护稳定行为时才有价值。仅复述赋值、Mock 调用或显然的框架接线的用例不形成有效回归保护。
5. 用户明确指定测试范围时按该范围执行。用户未指定时，由代理选择与风险相称的验证方式并继续工作。

## TDD 流程

决定新增测试后：

1. 把需求转成行为契约：输入、可观察输出、副作用、错误语义和不变量。
2. 选择最小有效边界：纯逻辑用单元测试，模块协作用集成测试，真实存储或队列语义用受控本地依赖。遗留重构用 characterization test 锁定需要保留的行为。
3. 写一个能够因为缺少目标行为而失败的测试，运行并确认失败原因与需求一致。
4. 写使该测试通过的最小生产代码。
5. 在测试保护下整理职责、命名和重复代码，并保持相关测试通过。
6. 覆盖关键边界和失败路径，再运行与影响范围相称的回归测试。

决定不新增测试后，选择能够直接证明改动正确的检查，例如 build、typecheck、lint、格式检查、配置渲染、模块启动、目标调用检查或现有回归测试。

## 测试设计

- 测试公开行为和稳定契约，不依赖私有方法或偶然实现顺序。
- Mock 外部边界和昂贵依赖，不 Mock 被验证的核心职责。优先使用项目现有 fixture、Provider mock 和可重复的本地数据。
- Bug 测试应在旧实现上稳定失败，并覆盖真正的触发条件。
- 测试数量服从风险覆盖，不追求每个文件、方法、配置项或代码变更都有新增用例。

## 完成标准

使用 TDD 时报告 RED 阶段的失败原因、GREEN 阶段的定向结果和最终回归范围。选择其他验证方式时，简要说明判断依据、实际检查和剩余风险。
